# Plan — #52: Automated PR review gate (agentic review as a required status check)

**Item:** `52` — Automated PR review gate: agentic review workflow as a required status check
**Source:** `cdhorne/claude-autopilot#52` · Scope: M · deps: none

## Problem & goal

The autonomous recipe (`ship.target: auto-merge-pr` + branch protection requiring `ci`)
merges on CI-green alone. The in-pipeline `shakedown-code` review runs *before* ship and
reviews the pipeline's own work in-context. The supervised out-of-band review has caught
things it missed (e.g. the `--from pick` silent no-op on #38). Unattended runs need that
second, **out-of-context** review as an *enforced* gate — a required status check named
`review` that sits alongside `ci` in branch protection.

Deliverable: a `pull_request` workflow that runs a bounded, fresh-session agentic review of
the PR diff, posts findings as a PR comment, and **exits non-zero iff a confirmed blocking
finding survives verification** — failing **closed** on any refusal / parse failure / SDK
error so an unattended run can never merge on a phantom sign-off.

## Scope

**In scope**
- New non-pipeline `Step` `pr-review` with first-class config (budget / turns / effort / model), mirroring the `shipwreck` precedent.
- New skill `.claude/skills/pr-review/SKILL.md` — a fresh-session, finder→verifier review producing a clean comment body + `Verdict: PASS|BLOCK`.
- New thin CLI `pr-review-cli.ts` (bin route `pr-review`) that runs the review via the existing `runStep` machinery, parses the gate, upserts the PR comment, and sets the exit code.
- New `parseReviewGate(text, ok)` helper (fail-closed) + unit tests.
- New workflow `.github/workflows/pr-review.yml` (self-hosted; same-repo PRs; job id `review`).
- Docs: `docs/pr-review.md` (gate + branch-protection setup), `docs/config.md` (new `pr-review` keys), one concise `CLAUDE.md` invariant note.

**Not in scope** (explicit follow-ups — see end)
- Closing the loop on failure (`autopilot --resume <id> --from implement` with findings as revision input) — the issue names this as a separate item.
- #34 notifications integration (park-for-attention UX). The gate merely goes red; wiring the alert is #34's job.
- Branch-protection *configuration* itself (a repo-admin action, documented not automated).

## Approach & key decisions

### 1. Reuse `runStep`; add `pr-review` as a non-pipeline `Step` (not a `PipelineStep`)

The issue mandates "via the existing SDK step-runner machinery." `runStep(name, prompt, opts, emit)`
resolves budget/turns/effort/model from `resolveStepSettings(CONFIG, profile, name)`, owns the
`query()` loop, **refusal detection** (`isRefusal` → `ok:false, subtype:"error_refusal"`), abort
handling, and event streaming. Running it with `cwd: REPO` yields **no worktree hooks and no
plan-block** (`isWorktreePath(REPO, REPO) === false`, `name !== "implement"`) — exactly the CI shape.

`Step` already models a config-carrying step that is *not* in the pipeline sequence: `shipwreck`
(`Step = PipelineStep | "shipwreck"`, present in `ALL_STEPS` and every `Record<Step, T>` map, absent
from `STEPS`). `pr-review` follows that precedent exactly:
- `config.ts`: `export type Step = PipelineStep | "shipwreck" | "pr-review";`
- `ALL_STEPS = [...STEPS, "shipwreck", "pr-review"]`
- Add a `pr-review` key to `DEFAULTS.budgets`, `DEFAULTS.turnLimits`, `DEFAULTS.effort`, and both `DEFAULTS.modelProfiles.standard` / `.quick`.

Because `pr-review` is **absent from `STEPS`/`PipelineStep`**, nothing that iterates the pipeline
sequence is affected: `shouldRun`/resume loops iterate `STEPS`; `isPipelineStep` gates `--from`
(so you can't resume *into* pr-review — correct); `detectResumeStep` validates against
`STEPS.indexOf` and pr-review never writes a pipeline log entry, so it can't reach that path.
`stats.ts` `STEP_ORDER` orders steps that appear in `.dev/autopilot-log.jsonl`; the standalone CI
review does not log a cycle there, so no change is needed.

*Alternative rejected:* a standalone `query()` call in `pr-review-cli.ts` avoids touching the `Step`
union but duplicates the SDK loop + refusal detection and violates the rubric's "no direct SDK
imports outside step-runner." The Step-addition is the sanctioned, contained path.

### 2. Single fresh session, finder→verifier as an internal three-phase discipline

The skill runs **one** `runStep("pr-review", …)` session structured as:
- **Phase A — find:** read the diff cold; read every changed file *in full* at head (not hunks); enumerate candidate findings against `_rubric.md` (Correct / Well-typed / Well-tested / Concise) + `CLAUDE.md` invariants.
- **Phase B — verify (adversarial):** switch stance to a skeptic whose job is to *refute* each candidate against the actual code; keep only findings that are (a) real and (b) **blocking** (ships a bug, breaks a load-bearing invariant, or merges broken code). Drop style nits, speculation, and anything not confirmable.
- **Phase C — report:** the final assistant message *is* the PR-comment body — short summary, the confirmed blocking findings (`file:line` + why + fix), then a trailing `Verdict: PASS` (no confirmed blockers) or `Verdict: BLOCK`.

One session keeps cost inside the ~$2–5 cap, yields one comment / one verdict / one exit code, and
respects Concise/YAGNI. *Alternative considered:* two separate `runStep` calls (independent
finder + independent verifier) — genuinely out-of-context per phase but ~2× cost and needs
finding hand-off plumbing. Deferred as an escalation only if precision proves inadequate; noted in
`docs/pr-review.md`. This is a v1 gate, not a deep audit.

The review is **read-only by convention** (the CI checkout is ephemeral; edits would never be
pushed), so `allowed-tools` is scoped to read/inspect (`Read Grep Glob Bash(git:*) Bash(gh:*)`) and
the CLI — not the agent — owns comment posting. No PreToolUse write-block is needed.

### 3. Fail-closed gate parsing — a dedicated helper, **not** `parseVerdict`

`parseVerdict` fails closed to `RETHINK` *unless* `reviewEngaged(text)` → `APPROVE`. That
"engaged ⇒ approve" fail-**safe** is wrong for a merge gate: a keyword-less-but-engaged review
would map to APPROVE → merge. A gate must fail closed to **block** on *any* ambiguity. New helper:

```ts
export function parseReviewGate(text: string, ok: boolean): "pass" | "block" {
	if (!ok) return "block"; // refusal / SDK error / max_turns / blocked → fail closed
	const m = text.match(/verdict[:\s*]+\*{0,2}(PASS|BLOCK)\b/i);
	if (m) return m[1].toLowerCase() as "pass" | "block";
	return "block"; // no explicit `Verdict: PASS` ⇒ block (no engagement fail-safe)
}
```

Only an explicit `Verdict: PASS` on an `ok` run passes; everything else blocks. Regex-driven +
pure ⇒ unit-tested (the rubric flags the `parseVerdict` family as failure-prone). Placed next to
`parseVerdict` in `helpers.ts`.

### 4. CLI owns diff-independent posting; gate maps to exit code

`pr-review-cli.ts` (mirrors `roadmap-cli.ts`):
1. Parse `--pr <n>` (required) via `node:util parseArgs`; profile defaults to `"standard"`.
2. `prompt = expandSkill("pr-review", \`--pr ${pr}\`)`; fresh `parkSignal`; minimal console `StepEmit`.
3. `result = await runStep("pr-review", prompt, { cwd: REPO, profile, trace: false, parkSignal, itemId: pr }, emit)`.
4. `gate = parseReviewGate(result.text, result.ok)`.
5. Upsert one PR comment: on `ok`, post `result.text` (the review) wrapped with a `<!-- autopilot-pr-review -->` marker + status header; on `!ok`, post a "review could not complete — **failing closed**" comment. Use `gh pr comment "$pr" --edit-last --create-if-none --body-file -` for idempotent re-runs on each push (mirrors the `publish-plan` single-comment idiom). *Caveat:* `--edit-last` edits the token user's most-recent comment, not the marker specifically — acceptable because the gate bot is the only thing posting via `GH_TOKEN` on autopilot PRs; the embedded marker leaves room for a marker-exact `gh api` upsert if `--edit-last` proves too blunt.
6. `process.exit(gate === "block" ? 1 : 0)`.

The agent produces the review; the CLI owns posting + exit code so a refused/crashed agent still
posts a red, failing check. Rate-limit → `ok:false` → block (transient; a human re-runs the
workflow — documented). Bin route added to `bin/claude-autopilot.js` `routes` + HELP.

### 5. Workflow: always-report required check, spend-guarded, same-repo only

`.github/workflows/pr-review.yml`:
- Trigger: `pull_request` (`opened, synchronize, reopened, ready_for_review`) targeting `main`. **No path filter** (path/branch filters + a *required* check strand PRs on a check that never reports).
- `concurrency: pr-review-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`.
- One job **`review`** (job id = required-check context), `runs-on: self-hosted` (needs `ANTHROPIC_API_KEY`; longer runtime), `permissions: { contents: read, pull-requests: write }`.
- The job **always runs to completion** so the `review` check always reports:
  - Fork / non-same-repo PR (`head.repo.full_name != repository`) or draft → skip the review, exit 0 (green). Secrets are unavailable to forks and forks can't be autopilot PRs.
  - Otherwise: checkout `ref: head.sha`, `fetch-depth: 0` (agent reads changed files at head and diffs `origin/main`); `pnpm install --frozen-lockfile`; run `npx @cdhorne/claude-autopilot pr-review --pr "${{ github.event.pull_request.number }}"` with `ANTHROPIC_API_KEY` + `GH_TOKEN`. The CLI exit code is the job result → the `review` check color.

Skipping *inside* the job (not via a job-level `if`) preserves required-check semantics: the check
is always created and always green/red, never perpetually pending. Same-repo guard avoids running
the agent on untrusted fork code on self-hosted infra.

## Test strategy

- **`parseReviewGate` unit tests** (`helpers.test.ts`, `node:test`):
  - `Verdict: PASS` + ok → `pass`; `**Verdict:** BLOCK` + ok → `block`; lowercase `verdict: pass` → `pass`.
  - Explicit `Verdict: PASS` but `ok:false` → `block` (ok-gate precedence).
  - Engaged review, no verdict keyword, ok → `block` (no engagement fail-safe — the key divergence from `parseVerdict`).
  - Empty / refusal-shaped text → `block`.
- **Config self-adjusts, no test edits needed.** `config.test.ts` asserts `deepEqual(cfg.budgets, DEFAULTS.budgets)` (and likewise turnLimits/effort/modelProfiles) — loaded-vs-`DEFAULTS`, so adding `pr-review` to `DEFAULTS` keeps both sides equal. No test hardcodes the `ALL_STEPS`/`Step` membership (verified). Optionally add one focused assertion mirroring the existing `resolveStepSettings` cases: `resolveStepSettings(CONFIG, "standard", "pr-review").budget === DEFAULTS.budgets["pr-review"]`.
- **check-skills** (`pnpm check:skills`) validates the new SKILL.md frontmatter, `!cat` include existence, and scoped-name usage.
- **Not unit-tested** (accepted per rubric — spawns real SDK / network): `pr-review-cli.ts` end-to-end, the workflow, and the live review. `runStep` reuse means the SDK loop is already covered by `step-runner.test.ts`.

## Rubric self-check

- **Correct** — Step-exhaustiveness upheld (all four `Record<Step,T>` maps + both profiles get `pr-review`; `ALL_STEPS` updated). Fail-closed gate is the load-bearing invariant, enforced in `parseReviewGate` (`!ok`→block, no-keyword→block) *and* by `runStep`'s refusal downgrade; documented in `CLAUDE.md`. No `STEPS` pollution ⇒ pipeline sequencing untouched. `expandSkill` frontmatter-strip unaffected (skill body is self-contained; `!cat` includes follow the existing plan/shakedown idiom).
- **Well-typed** — `parseReviewGate` returns a `"pass" | "block"` literal union; `Step` stays a literal union; no `any`; explicit return types on the new exported functions.
- **Well-factored** — logic lands on the right layer: config in `config.ts`, pure parser in `helpers.ts`, SDK loop stays in `step-runner.ts` (reused, not duplicated), the CLI is a thin entry beside `roadmap-cli.ts`. No new abstraction — `runStep` is extended by data (a new step), not by new code paths.
- **Well-tested** — the failure-prone regex parser gets the same unit-test treatment as the `parseVerdict` family; SDK-integration surface is left untested per the rubric's stated exception.
- **Concise** — no config knob beyond the four standard per-step maps; single-session review (not speculative two-session orchestration); CLI reuses `runStep` and `expandSkill` rather than re-implementing them.
- **Idioms** — deferred to `/shakedown` (out-of-context). Flag for it: workflow pinning/permissions conventions vs. existing workflows, and the single-session-vs-two-session finder→verifier call.
