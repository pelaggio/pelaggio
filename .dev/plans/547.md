# Plan: Resource-bounded discovery fleet (#547)

## Outcome and scope

Replace the label-by-label PR-review discovery launcher with one typed discovery-fleet planner and
one structured executor. The executor schedules every selected `(iteration, lens, driver)` cell in
stable order, overlaps cells whose fixed resource claims are compatible, and preserves the proven
Claude-before-Grok full-settlement edge. Verification remains a separate, sequential phase with its
current deterministic mutation and reconciliation semantics.

This is the smallest safe slice that removes the outer label barrier and establishes a construction
chokepoint for later resource configuration, authenticated cell resume, telemetry, and review-policy
work. It does not change which reviews run, provider diversity, prompt contents, finding severity,
verification order, convergence, evidence authority, or final publishing.

## Hardening sequence

1. **#746 — semantic red-team trigger:** remove noisy syntactic triggers and measure trigger yield.
2. **#547 — this plan:** establish the typed discovery cell and resource-aware execution funnel while
   retaining known-safe provider compatibility.
3. **Resource controls:** expose a total seat limit plus limits keyed by opaque provider-declared
   resources. Detect an explicit capacity/boot failure only when overlapping claimants were active,
   then recommend a lower exact setting. Never auto-tune or retry with changed limits.
4. **#511 + cell resume:** persist each completed cell through the authenticated evidence seam and
   reuse only an exact head/diff/prompt/config/verifier binding.
5. **#640 — observation:** measure per-cell elapsed time, token/cache availability, failures, and
   unique adversarial yield in an observational record separate from verdict authority.
6. **Adversarial rubric:** ask reviewers for concrete bypasses of named chokepoints, misleading or
   unbound evidence, and violations of adopted repository/protocol standards. Factoring advice stays
   non-blocking unless it demonstrates a correctness, security, integrity, or load-bearing
   completeness failure.
7. **#757 — intensity:** use the same planner for any later conservatively reduced review matrix.

This order makes each PR independently reviewable. The typed cell and resource seam lands before any
configuration, cache authority, or policy consumes it.

## Evidence behind the shape

The saved #778 rolls contain at least five verified blocker classes found only by the red-team lens:
the Git-submodule host-consent bypass, Grok shared-leader escape, expiring request-claim race,
illegal journal completion, and case-insensitive policy-path bypass. Both Codex and Grok contributed
unique findings. A standard finding must therefore never cancel another selected discovery cell.

#779 showed the cost of the current outer label barrier: standard cells completed before red-team
began, so their work could not overlap later discovery and was lost when the process was interrupted.
This slice reduces that serial latency. It does not claim interruption durability; that requires the
authenticated per-cell evidence follow-up after #511.

The #434 Claude/Grok concurrent-boot defect is also established. #547 retains full Claude settlement
before any Grok launch. Narrowing that edge requires the deferred real-host readiness experiment and
its own review.

## Settled decisions

`DECISION: slice boundary | chose: discovery planning and bounded execution only | alternatives: combine configuration, diagnostics, persistence, metrics, readiness APIs, and prompt policy in #547`

The combined design spans config, provider protocols, evidence authority, metrics, and review
policy. That scope is likely to produce several independent blocker classes and expensive rerolls.
The discovery executor is independently useful and is the prerequisite chokepoint for every later
slice.

`DECISION: execution order | chose: schedule the complete selected discovery matrix through fixed resource claims | alternatives: run red-team first and stop on a blocker; keep complete labels serial; launch every cell immediately`

Red-team-first withholds ordinary correctness findings until another revision. Whole-matrix
scheduling gives the author one complete discovery set while a fixed resource ledger prevents
unbounded fan-out. Stable plan order controls admission ties and aggregation; completion timing
never changes the verdict.

`DECISION: resource identity | chose: opaque registry-declared resource keys with conservative fixed capacities | alternatives: provider-name keys; public limits in this slice; one global semaphore`

Provider name is not a durable resource identity: accounts, backends, models, and host boot paths may
share or separate constraints. Each review-capable provider declares a closed set of opaque resource
claims. #547 fixes each provider-session resource at capacity one and sets the global active-seat
capacity to the number of configured review drivers. The existing Claude/Grok compatibility edge is
an additional dependency, not a hidden provider conditional in the executor. Unknown or
unsatisfiable claims fail before launch. The resource-controls child will add user settings and
warnings without changing cell identity.

`DECISION: verification boundary | chose: complete all discovery, then run current verification serially in configured cell order | alternatives: dynamically enqueue verifiers during discovery`

`runVerificationPass` currently mutates shared survivor/disposition state. Overlapping it with
discovery or another verifier could make authorization depend on completion order. This slice makes
discovery results immutable and dense, then hands them to the existing sequential verification and
reconciliation loop. Parallel verification requires a later immutable-result design.

## Approach

### 1. Define the discovery fleet once as typed data

Add a pure `review/discovery-fleet.ts` module with closed types for:

- stable cell identity: iteration, `standard | red-team` lens, and configured driver identity;
- immutable planned/running/settled lifecycle states;
- opaque resource key and positive claim count;
- fixed capacity table and explicit dependency edges;
- dense, stable result slots in configured lens-then-driver order.

`buildDiscoveryFleetPlan` is the sole matrix, identity, and resource-plan authority. It receives the
already computed lens list and resolved drivers, so it does not classify security, construct prompts,
or inspect config. It rejects duplicate cell keys, duplicate or unknown resource declarations,
non-positive/unsatisfiable claims, missing dependencies, and dependency cycles before any provider
starts.

Extend the existing provider registry descriptor with review resource metadata. Start with one opaque
session key per provider at capacity one. Express the current Claude→Grok exclusion as a dependency
derived in the planner from registry compatibility data. Keep provider names and protocol decisions
out of the executor.

### 2. Make one executor own discovery launch and settlement

Add `executeDiscoveryFleet(plan, launch, signal)` in the same module. It is the only function in the
cold gate that launches discovery cells.

- Admit ready cells deterministically when every resource claim fits the fixed ledger.
- Attach fulfillment/rejection observation at promise creation, including synchronous launch throws.
- Release each claim exactly once when its cell reaches a terminal settled state.
- Start a newly eligible cell as soon as resources and dependencies allow; do not wait for its entire
  lens to finish.
- Stop admitting new cells after park/cancel, but await every already-started child before returning.
- Merge child park telemetry with the existing earliest-positive-reset rule.
- Return a dense result vector in plan order regardless of completion order.
- Represent a missing, rejected, or invalid slot with the same fail-closed result shape the gate uses
  today.

Keep iterations sequential. The gate builds iteration N+1 only after discovery, sequential
verification, and convergence for iteration N complete.

### 3. Route the cold gate through the chokepoint

Replace `settleDiscoveryLaunches` and the nested per-label launch loop in `runPrReviewGate` with:

1. construct every selected prompt and cell for the current iteration;
2. build and validate one discovery plan;
3. execute it through `executeDiscoveryFleet`;
4. convert settled slots into immutable `ReviewPass` values in stable plan order;
5. preserve the existing park check;
6. run the existing sequential verification and convergence logic unchanged.

Direct CLI, review drain, and ship preflight already call `runPrReviewGate`; they receive the new
executor by construction. Add a module-boundary conformance test that permits cold discovery launch
only through `executeDiscoveryFleet`, rather than maintaining a brittle list of callers.

The executor may emit concise live progress using the gate's existing output seam: planned cell,
resource/dependency wait, start, and settlement. Output contains only typed identifiers and outcome,
never prompts or model prose. No new record schema or publisher is added in this slice.

### 4. Preserve the known-safe Claude/Grok rule exactly

For a fleet containing Claude and Grok, all non-Grok cells may use their independent resources, but
each Grok cell depends on settlement of every Claude discovery cell in that iteration. This matches
the current full-seat safety rule across the newly flattened lens matrix. Codex can overlap either
phase. A missing/failed Claude cell still settles the dependency and then fails the gate through the
existing typed result; it does not leave the executor hung.

Do not add `onProviderReady`, edit adapter lifecycle semantics, or perform a real-provider
concurrency drill in #547. The deferred readiness item will first record the host experiment, then
introduce the smallest callback needed to narrow this explicit edge, with full settlement as the
fallback.

### 5. Present one stable candidate to the expensive gate

Land #746 first and rebase once. Implement only this slice in the isolated #547 worktree. Keep the
PR unopened until exact gate-parity fixtures, adversarial scheduler tests, docs, and full repository
validation pass. Run a fresh shakedown focused on the launch chokepoint, resource-release invariants,
park/cancel behavior, and absence of new authority or provider-protocol surfaces.

Open the PR at one stable candidate SHA and run the complete provider-diverse gate once. If it finds
blockers, hold further pushes, fix and locally validate the whole confirmed set together, then use
the narrow interdiff adjudication path for that single revision when its preconditions hold. If a
finding requires broader authority or provider lifecycle work, move it to the appropriate deferred
item rather than adding a call-site patch. Do not plan on an administrative merge bypass.

## Test strategy

### Planner and resource ledger

- A security-selected two-driver iteration produces exactly four unique cells in stable
  standard/driver-order then red-team/driver-order.
- Unknown resources, duplicate identities/declarations, zero/negative/excessive claims,
  unsatisfiable capacity, missing dependencies, and cycles fail before any launch.
- A new review-capable provider without resource metadata fails the exhaustive registry/conformance
  check instead of receiving implicit unlimited capacity.
- Fixed capacity one serializes cells sharing a session resource; independent resources overlap up to
  the fixed global capacity.

### Structured concurrency and falsifiers

- Controlled promises prove a settled standard cell releases its resource to the matching red-team
  cell without waiting for another provider's standard cell.
- A synchronous launch throw and asynchronous rejection are observed immediately and occupy the
  correct dense result slot.
- Abort or park during admission starts no new cells, awaits all started promises, merges child park
  state deterministically, and releases resources exactly once.
- A hung cell plus cancellation cannot allow an incompatible dependent to start or leave an
  unobserved rejection.
- Randomized completion orders produce identical result order, finding order, agreement, and verdict.
- Invalid plans start zero providers.

### Gate parity and compatibility

- Existing standard-only and standard-plus-red-team fixtures produce the same prompts, `ReviewPass`
  semantics, verification order, agreement, survivors, comments, status, cost, and turns.
- A blocker in any standard cell does not suppress selected sibling or red-team discovery cells.
- Claude/Grok tests prove every Grok discovery waits for every Claude discovery to settle across
  labels; Codex may overlap; Claude failure/park cannot deadlock the fleet.
- Verification begins only after the complete dense discovery fleet and remains serial in configured
  cell order.
- The module conformance test fails if cold-gate discovery gains a second launch path.
- Run focused tests with the dot reporter, then `pnpm -r test`, `pnpm typecheck`,
  `pnpm typecheck:ratchet`, `pnpm check`, `pnpm check:skills`, `pnpm check:publish`, and
  `pnpm test:ci`.

## Rollout and falsifiers

1. Land #746 and rebase #547 once.
2. Land planner/executor and parity tests with the existing Claude/Grok settlement edge.
3. Enable the flattened discovery matrix with fixed provider-session capacity one.
4. Observe 20 eligible rolls before the resource-controls child chooses config defaults or warning
   thresholds. Feed timings and failures to #640 without inferring absent historical cell data.

Wrong-if conditions:

- If the executor cannot own every cold discovery launch, do not claim the chokepoint; route the
  bypass or narrow the guarantee and conformance test first.
- If flattening changes prompts, verification order, convergence, or published verdict bytes, treat
  it as a blocker and restore parity before opening the PR.
- If cross-provider overlap increases protocol failures, lower the fixed global capacity in this
  slice and let the resource-controls child expose operator limits with evidence.
- If opaque resource metadata requires adapter lifecycle changes, keep a local exhaustive mapping in
  the provider registry for #547 and defer the capability refactor.
- If the implementation exceeds a coherent M slice after source inspection, split the live-progress
  output first; preserve the planner/executor and safety tests as the shippable core.

## Rubric self-check

- **Correct:** every selected discovery cell still runs; verification, convergence, failure closure,
  parking, stable rendering, and Claude/Grok settlement semantics remain intact.
- **Well-typed:** cell states, opaque resource claims, capacities, dependencies, and settled slots are
  closed data. Unknown or incomplete plans fail before launch or fail the gate.
- **Well-factored:** `buildDiscoveryFleetPlan` is the only matrix/resource authority and
  `executeDiscoveryFleet` is the only cold discovery launcher. Provider constraints enter as
  exhaustive registry data.
- **Well-tested:** controlled-promise tests cover concurrency, hangs, cancellation, synchronous
  throws, exact resource release, deterministic ordering, and zero-start invalid plans; legacy
  fixtures prove behavior parity.
- **Concise:** one new pure module and a narrow gate integration establish the seam. Configuration,
  telemetry, authenticated reuse, readiness protocols, and prompt policy are explicitly deferred.
